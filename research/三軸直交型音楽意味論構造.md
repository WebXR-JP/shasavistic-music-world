# 三次元直交ベースのシャサフ式音楽モデル設計案

## 1. 基本方針

曲全体を単純な入れ子構造としてではなく、次の3軸が直交する時空間として扱う。

| 軸 | 意味 | 例 |
|---|---|---|
| X | 時間 | 小節・拍・時刻 |
| Y | Track / Voice | Melody、Bass、Pad、Voice 1… |
| Z | Musical Context | 主次元・解音・法音・Harmony など |

Track と Musical Context は互いを所有しない。

任意時刻 `t` において、

`MusicalContext(t) × Track(t)`

の交点から、その時点での発音内容を解決する。

---

# 2. 音楽理論上の依存構造

基本となる強い依存関係は次の通りとする。

GlobalPitch
↓
PrimaryDimension
↓
ResolutionTone
↓
PitchSpace / Scale

ここから、法音と Harmony は分岐する。

PitchSpace / Scale
├─ ModalTone
└─ Harmony

つまり、

`Harmony は ModalTone に依存しない`

ことを基本原則とする。

ただし法音は、

- Harmony の安定度
- 機能
- 解決傾向
- 中心からの距離

などを評価する際には利用できる。

したがって、

ModalTone
↓
HarmonyEvaluation

という別の依存関係を持つ。

全体としては、

GlobalPitch
↓
PrimaryDimension
↓
ResolutionTone
↓
PitchSpace / Scale
├─────────────┬─────────────┐
↓             ↓
ModalTone     Harmony
│             │
└──────┬──────┘
       ↓
HarmonyEvaluation

となる。

---

# 3. GlobalPitch

`GlobalPitch` は全音高体系を物理周波数空間へ写像する基準である。

例：

GlobalPitch = 440 Hz

GlobalPitch は特定の和音・解音・法音には属さない。

論理音高から最終周波数を得る際、

Frequency = GlobalPitch × PitchRatio

として利用する。

## GlobalPitch の特殊性

GlobalPitch の変更だけは、現在発音中のすべての有音高音へリアルタイムに反映する。

例えば、

440 Hz → 442 Hz

と変更された場合、

- Melody
- Bass
- Chord Voice
- Arpeggio
- 持続音

を含むすべての音が同じ比率で移動する。

したがって発音時に Hz を完全固定するのではなく、

LatchedPitchRatio

を保持し、

frequency(t)
    = globalPitch(t)
    × latchedPitchRatio

として再生する。

---

# 4. PrimaryDimension

`PrimaryDimension` は、その区間で主として使用される次元体系を表す。

例：

- 3D
- 4D
- 5D

PrimaryDimension は単なるタグではなく、

- 使用可能な格子
- 音高関係
- 音階生成
- Harmony の構造候補

を制約する。

GlobalPitch
+
PrimaryDimension
↓
PitchLattice

という形で格子空間を生成する。

---

# 5. ResolutionTone / 解音

解音は任意周波数として指定できない。

必ず、

`GlobalPitch + PrimaryDimension`

によって生成された `PitchLattice` 上の点から選択する。

したがって、

ResolutionTone {
    coordinate: LatticeCoordinate
}

のように表現し、

frequency: number

を直接保持しない。

実際の周波数は、

ResolutionFrequency
    =
GlobalPitch
×
ratioOf(ResolutionTone.coordinate)

として導出する。

これにより、

GlobalPitch変更
↓
格子全体が物理周波数上で移動
↓
解音も移動
↓
全発音がリアルタイム追従

という構造を自然に実現できる。

---

# 6. PitchSpace

`PitchSpace` は、

PrimaryDimension
+
ResolutionTone

から導出される論理音高空間である。

PitchSpace は、

- 解音を原点とした格子座標
- 利用可能な次元関係
- 音高比
- 和音構築可能性

などを提供する。

Harmony は原則としてこの PitchSpace 上に定義される。

つまり、

PrimaryDimension
+
ResolutionTone
↓
PitchSpace
↓
Harmony

という依存になる。

---

# 7. Scale

Scale は、

PrimaryDimension
+
ResolutionTone

から導出される音階集合である。

PitchSpace 全体と Scale は同一ではない。

PitchSpace
→ 理論上利用可能な音高空間

Scale
→ その中から音楽的に選択された音集合

とする。

Scale {
    degrees: ScaleDegree[]
}

のような表現を持つ。

---

# 8. ModalTone / 法音

法音は任意の PitchCoordinate から選択しない。

必ず現在の Scale に含まれる音から選択する。

PrimaryDimension
+
ResolutionTone
↓
Scale
↓
ModalTone

したがって、

ModalTone {
    degree: ScaleDegreeId
}

のように、

`ScaleMember`

として表現する。

これにより、

「現在の音階に存在しない音を法音として設定する」

という不正状態を防ぐ。

---

# 9. 法音と Harmony の関係

法音と Harmony は直接の親子関係を持たない。

両方とも同じ PitchSpace を共有する。

PitchSpace
├─ ModalTone
└─ Harmony

例えば法音が変更されても、

同じ Harmony の論理構造をそのまま維持することができる。

ただし、法音が変化すると、

- Harmony の中心性
- 安定度
- 緊張度
- 解決方向
- モード上の機能

などの評価結果は変化し得る。

したがって、

Harmony

と

HarmonyEvaluation

を分離する。

Harmony
→ 音高構造そのもの

HarmonyEvaluation
→ 現在の ModalTone や前後関係から得られる音楽的評価

とする。

---

# 10. Harmony

Harmony は絶対 PitchCoordinate の集合としてではなく、

`ResolutionTone / PitchSpace`

に対する相対構造として記述する。

例えば、

Harmony {
    root: RelativeLatticeCoordinate
    structure: ChordStructure
}

のようにする。

重要なのは、

`root = ModalTone + offset`

を Harmony の基本表現にはしないこと。

法音は Harmony の存在条件ではないため、

Harmony の基準は、

- 解音
- PitchSpace
- 和音自身の基音

などから構成する。

例えば、

HarmonyRoot
    =
ResolutionTone
+
RelativeLatticeCoordinate

とする。

---

# 11. HarmonyEvaluation

Harmony の機能的意味は別途評価する。

HarmonyEvaluation {
    stability
    tension
    modalFunction
    tendency
    distanceFromModalCenter
}

評価には、

- ModalTone
- Scale
- PreviousHarmony
- NextHarmony
- Melody
- Bass

などを利用できる。

概念的には、

evaluateHarmony(
    harmony,
    modalTone,
    scale,
    surroundingHarmony
)

のようになる。

これにより、

同じ Harmony でも法音によって異なる機能として解釈できる。

---

# 12. HarmonyRegion

Harmony は瞬間 Event ではなく、

「一定区間において成立している和声状態」

として扱う。

HarmonyRegion {
    range: TimeRange
    harmony: Harmony
}

例えば、

0..4   : H0
4..8   : H1
8..12  : H2

となる。

HarmonyRegion は Track を所有しない。

同じ HarmonyRegion が同時に、

- MelodyTrack
- BassTrack
- PadTrack
- ArpeggioTrack
- VoiceTrack

へ作用する。

---

# 13. Musical Context の時間構造

以下の各要素は、境界を共有する必要がない。

PrimaryDimensionTimeline

|-------------------- 3D --------------------|

ResolutionToneTimeline

|------------ R0 ------------|------- R1 ------|

ModalToneTimeline

|---- M0 ----|--------- M1 ---------|--- M2 ---|

HarmonyTimeline

|- H0 -|- H1 -|--- H2 ---|- H3 -|- H4 -|- H5 -|

つまり、

`時間区間としては独立`

している。

ただし意味論上は、

PrimaryDimension
↓
ResolutionTone
↓
PitchSpace

という依存を持つ。

ModalTone と Harmony は、その PitchSpace 上の別々の状態として扱う。

---

# 14. Track

Track は Musical Context とは独立した軸として扱う。

Track {
    events: NoteEvent[]
}

例えば、

- MelodyTrack
- BassTrack
- VoiceTrack
- ArpeggioTrack

など。

Track は解音・法音・Harmony を所有しない。

任意時刻 `t` で Musical Context を参照する。

---

# 15. 三次元直交モデル

全体は、

X = Time
Y = Track
Z = Musical Context

の3次元モデルとして扱える。

                Musical Context Z
                       ↑
                       │
                       │
MelodyTrack ──────────┼────────────→ Time X
BassTrack   ──────────┼────────────
PadTrack    ──────────┼────────────
                       │
                       ↓
                     Track Y

Musical Context 側には、

- PrimaryDimension
- ResolutionTone
- Scale
- ModalTone
- Harmony

が存在する。

Track と Harmony は包含関係ではなく、

`時間座標によって交差する`

関係になる。

---

# 16. Note の PitchIntent

Note の作曲上の意味は `PitchIntent` として保持する。

例：

PreviousNote + 2D

ChordRoot

ChordTone[2]

ModalTone + 3D

ResolutionTone + latticeOffset

など。

つまり Note は、

「何を基準としてこの音が選ばれたか」

を任意に保持できる。

---

# 17. NoteOn 時の解決

NoteOn 時点 `t` で、

PrimaryDimension(t)

ResolutionTone(t)

Scale(t)

ModalTone(t)

Harmony(t)

を取得する。

その後、

PitchIntent

を解決して、

LogicalPitch

を得る。

最終的に、

LatchedPitchRatio
    =
ratioFromGlobalPitch(LogicalPitch)

としてラッチする。

---

# 18. 発音後の変更挙動

変更ごとの挙動は次の通り。

| 変更対象 | 発音済みノート | 新規ノート |
|---|---|---|
| GlobalPitch | リアルタイム追従 | 新値を使用 |
| PrimaryDimension | 影響なし | 新次元で解決 |
| ResolutionTone | 影響なし | 新解音で解決 |
| ModalTone | 影響なし | 新法音を参照 |
| Harmony | 影響なし | 新Harmonyを参照 |

つまり、

PrimaryDimension
ResolutionTone
ModalTone
Harmony

は NoteOn 時に意味解決される。

一方、

GlobalPitch

だけは発音中も参照し続ける。

---

# 19. Harmony の発音

Harmony 自体は発音 Event ではない。

HarmonyRegion
↓
Voicing / Arrangement
↓
NoteEvent[]

という流れで実際の音へ変換する。

例えば同じ Harmony でも、

- Close Voicing
- Open Voicing
- Arpeggio
- Spread
- Drop Voicing

などを別 Track として実現できる。

Harmony は「何が成立しているか」を表し、

Track は「それをどう鳴らすか」を表す。

---

# 20. Bass と Melody

Bass と Melody は Harmony の子にしない。

両方とも独立 Track とする。

ただし PitchIntent の生成規則が異なる。

## Melody

主に、

- PreviousNote
- ModalTone
- Scale
- Harmony

を参照する。

特に時間方向の連続性を強く持つ。

## Bass

主に、

- HarmonyRoot
- PreviousBass
- ResolutionTone
- Scale

を参照する。

Harmony との結びつきは Melody より強いが、

BassTrack 自体は Harmony の所有物ではない。

---

# 21. 型上の不変条件

以下は型システムまたはバリデーションで保証する。

ResolutionTone
∈
PitchLattice(GlobalPitch, PrimaryDimension)

ModalTone
∈
Scale(PrimaryDimension, ResolutionTone)

Harmony
∈
PitchSpace(PrimaryDimension, ResolutionTone)

重要なのは、

ModalTone
→ Harmony

という制約を置かないこと。

つまり Harmony が成立するために法音は必要ない。

---

# 25. 設計上の中心原則

このモデルでは、

**解音は音高空間の原点**

**法音は音階内の知覚的・旋法的中心**

**Harmony は解音基準の音高空間上に成立する相対和声構造**

として明確に分離する。

したがって、

`法音が変われば Harmony が変わる`

とは限らない。

変化するのはむしろ、

`同じ Harmony をどう解釈するか`

である。

この分離によって、

- 法音変更
- モード変更
- コード進行
- 解音変更
- 次元変更

を互いに過剰に結合せず表現できる。

また、

`Time × Track × MusicalContext`

という三次元直交モデルを維持したまま、シャサフ式の音高構造と一般的なシーケンサー構造を両立できる。
