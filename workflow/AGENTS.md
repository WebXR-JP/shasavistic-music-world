# 設計と検証の運用

この文書はworkflow/AGENTS.mdに置く正本であり、シャサフ式音楽を試すXRiftワールドプロジェクトの設計と検証の管理範囲と基本規則を定める。上位規則はAGENTS.mdによる。

## 管理範囲

| 階層 | 答えること | 配置 |
|---|---|---|
| Design | 要求をなぜこの方式で満たすか | workflow/designまたは各部の設計置場 |
| Spec | 採用する設計の振る舞いをどう判定するか | テストコード、fixture検証、機械可読な実行証拠 |
| 一時的な検証計画 | まだ実行形で表せない受入れ条件 | workflow/spec |

調査資料と候補の置場は決定の正本ではない。

## 基本規則

- 設計は対応する承認済みの要求元を参照し、要求を再定義しない。要求正本がある場合はその文書を参照し、ない場合は依頼・課題・受入れ条件を参照する
- 判断の正本は一箇所にする。調査資料、親設計、子設計へ結論を複製しない
- 確定した判断、未確定の候補、採用を見直す条件を区別する
- 計測、観測、外部仕様を根拠にする場合は参照元と確認状態を記録する
- 入力例、期待値、境界値、合否判定はテスト名、テストの説明、テスト本体の検証式、fixture検証へ置く。具体値を別文書へ複製しない
- テスト名は保証する振る舞いを表す。前提や合格条件を名前だけで表せない場合は、説明で補う
- テストから生成する文書は閲覧用とし、正本として管理しない
- 受入れ条件を実行形で表せない期間だけ検証置場に計画を置いてよい。未実装条件、必要な環境、残す証拠だけを記載し、対応するテストまたは証拠の判定処理が完成した項目から削除する。項目がなくなった文書は廃止する。詳細はworkflow/spec/AGENTS.mdによる
- 実行できない空の検証や、常に成功する検証を計画の代わりに置かない
- 実機や人間の確認を要する検証も、長期的には実行手順と合否判定を実行側へ移し、結果を機械可読な証拠として残す
- 要求内容の変更が必要な場合は設計で補わず、人間の判断へ戻す
- 設計の作成や変更後はworkflow/design/AGENTS.mdに従って審査する
