# デバッグの指針

## 目的と判断基準

AIが実際の操作と知覚できる結果を確認し、人間へ引き渡した後の不具合発見と手戻りを減らす。理想は、人間が気づく問題にAIも気づき、自律的に修正・検証できることである。

最適化するのは、AIのトークン消費、人間の操作・判断・待ち時間、環境の構築・保守、見逃しによる手戻りを含む総労力である。ログや検証回数を減らすだけで、問題発見を人間へ押し戻してはならない。

日常のデバッグでは以下の方針を使う。診断機構や操作API、再現環境の設計担当は、[環境整備の指針](references/debug-environment.md)も読む。実行担当は委譲された実装に必要な部分を参照する。

## 設計・判断と実行の分担

このスキルを読むこと自体は、設計責任の委任を意味しない。以下の検証原則は全員で共有し、仮説・観測方法・判定基準・修正方針の選択や変更は設計・判断担当が担う。

- **設計・判断担当**は、抽象的な判断に適した上位モデルが担う。次に何を明らかにするかを決め、必要な環境整備を設計し、証拠から継続・再計画・完了を判断する。
- **実行担当**は、決まった計画に沿って再現・計測・証拠収集・限定した実装を行う。設計済みの観測点を追加する実装も委譲できる。目的と許可範囲を変えない局所的な実装判断は、担当内で進める。
- **進行管理**は、計画済みの分岐を進め、想定外の結果を設計・判断担当へ戻す。単純な遷移や定型処理は既存機能やスクリプトを使い、毎回モデルに判断させない。

分担は調査全体に一度だけ適用するものではない。実行中に設計が必要になれば設計担当へ戻し、計画が具体化したら再び実行担当へ渡す。単純な作業を不必要に分割せず、設計判断のある箇所を境界にする。

### 実行担当への委譲と差し戻し

委譲時は、目的、利用する手段、変更可能な範囲、必要な証拠と終了条件、試行上限を短く伝える。実行担当には今回必要な情報を渡し、設計担当は調査全体の仮説と棄却理由を保持する。

実行担当は次の場合、証拠と不足事項を添えて設計・判断担当へ戻す。独自に計画や環境の構造を変更して解決を試みない。

- 必要な観測手段がない、または取得した証拠では指定の判定ができない。
- 計画にない結果や矛盾が生じた、または変更範囲を広げる必要がある。
- 決められた試行上限に達しても終了条件を満たせない。

結果には、実行内容・証拠・変更箇所と、計測完了／観測不足／想定外／実行失敗などの状態を示す。計測完了を不具合の解決と同一視しない。差し戻しは原則としてエージェント間で処理し、人間には要求や許容範囲など、人間の判断が必要な点を確認する。

## 何をもって正常とするか

調査の起点を「どの条件・操作で、何が起きるべきで、実際にはどう違うか」に置く。見た目や操作感は、必要に応じて参照画像、操作例、許容範囲で具体化する。基準が未定の価値判断は人間に確認し、再現や証拠収集はAIが進める。

AIの見逃しは、次のどこで起きたかを切り分ける。

| 不足しているもの | 改善するもの |
|---|---|
| 問題が起きる条件を再現していない | 入力、操作順、端末、実行環境 |
| 問題が観測できない | 画像、時系列、内部状態の取得手段 |
| 正常・異常の基準がない、基準が違う | 期待結果、比較対象、許容範囲 |
| 証拠と基準が揃っても判断を誤る | 証拠の提示方法、機械判定、モデルや人間による評価 |

内部状態が正常でも、利用者が見る結果の正常性を保証したことにはならない。静止画で分からないちらつきや遅延には、時系列の観測を使う。

## 問題を判定できる最も安価な層を使う

低い層で検出できる問題は、型や自動検査で早く捕捉する。ただし、以下は全段階を毎回実行する手順ではない。既存の証拠を起点に、不足があれば症状を直接観測できる層を使い、原因と再発防止に適した層へ絞り込む。

| 層 | 主に確認すること |
|---|---|
| 型・コンパイル時検査 | 不正な状態、意味・単位の取り違え、表現上の制約 |
| 単体テスト | 計算、境界条件、状態遷移などの振る舞い |
| 統合テスト | モジュール間やCPU・GPU間のデータ受け渡しと実行経路 |
| E2Eテスト | 利用者の操作から、画面や保存結果などへ至る一連の振る舞い |
| 実機操作・画像・録画の確認 | 見え方、操作感、端末固有の挙動、自動判定から漏れた問題 |

コード上の制約は[code-writing](../writing/code-writing/SKILL.md)と対象言語のスキルに従う。

### テストの価値を保つ

各テストが「どの失敗を防ぐか」を説明できるようにする。実装の処理をそのまま書き直した期待値や、内部関数が呼ばれたことだけで利用者の成功を判定するテストを避ける。

E2Eテストは、利用者の操作・期待結果・判定根拠を人間が理解できる形にする。人間は要求や許容範囲の妥当性を確認し、AIはそれを実際に検証できる経路と判定を整える。

下位のテストで原因を狭く検出し、上位のテストで接続と利用者の結果を確かめる構成は、同じ機能を扱っていても役割が異なる。重複は検出する失敗と経路で判断し、件数だけで増減しない。

### 実際の利用経路を確かめる

自動操作は本番と共通の処理を通す。状態の直接書き換えやテスト専用の近道で成功しても、省略した入力・描画・ライフサイクルを検証したとは扱わない。クリックやフォーカスの問題では実際の入力経路を通す。

手動操作でだけ失敗する場合は、入力、タイミング、環境、判定対象の差を調べる。描画や操作に関わる修正は、変更した経路の実際の結果をAIが確認する。確認できない範囲は未確認として示す。

最終的な画面確認で初めて問題が見つかったら、検出の不足を見直す。繰り返し起こる問題は安価な検査へ移すが、画面確認で新しい問題を発見する余地は残す。

## 調査の反復と完了

既存の調査、成果物の同一性、並行変更の確認などは、適用されるAGENTS.mdの検証規律に従う。

次の検証で何を判別するかを決め、仮説を区別できる小さな実験を選ぶ。新しい情報が得られない再実行は重ねず、観測方法や再現条件を変える。再現率を調べる反復では、回数と成功・失敗を記録する。

再現しない問題では、影響と調査費用に応じて試行範囲を決める。追加観測にも進めない場合は、未解決のまま根拠と再開に必要な条件を示し、再現しないことを解決の根拠にしない。

完了報告では、対象条件で期待結果を確認した根拠と残る未確認事項を示す。テスト通過の範囲を超えて「問題がない」と一般化しない。再発防止は、その失敗を検出できる最小限の検査や制約にする。
