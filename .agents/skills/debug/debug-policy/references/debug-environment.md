# デバッグ環境の整備

この文書の設計判断は、[役割分担](../SKILL.md#設計判断と実行の分担)に従って設計・判断担当が行う。実行担当は、委譲された設計を実装・検証するために参照する。

## 投資する範囲を決める

まず既存のログ、診断機能、テスト、操作手段を探す。追加する仕組みは「何が見えず、どの繰り返し作業を減らすか」を明確にする。

繰り返しの頻度、見逃した場合の影響、削減できる作業と、構築・実行・保守の負担を比較する。一度の調査に十分な一時的な計測も許容し、再利用の見込みがある部分を共通化する。今回必要な観測を越えて汎用基盤を作り込まない。

作る際においては、既存のデバッグの仕組みが適切かどうかについても必ず考える。ログを吐きまくるだけの既存の仕組みを放置して独立したデバッグ機構を追加するなどは避け、同様の内容を検証可能にしつつより構造的に優れた仕組みに統合できないかについて検討する。

導入後は、人間への操作依頼、原因特定までの再実行、読み込む証拠量など、減らしたかった負担が実際に減ったかを振り返る。測定のための作業も必要最小限にする。

## 進行管理の仕組みを複雑にしすぎない

ハーネスによる自動振り分けや実行担当の制約にも、構築・理解・保守の負担がある。少数の役割、短い委譲内容、明示した差し戻し条件から始め、既存のエージェント・権限・実行機能を優先する。

制約の自動検査は、観測された逸脱や繰り返す手戻りに対して効果のある境界へ絞る。すべての操作を分類・監視する汎用機構や、些細な実装判断ごとの承認を前提にしない。追加する制御で何を防ぎ、保守負担に見合うかを説明できるようにする。

少数の明確な状態で実行中・設計判断待ち・人間の入力待ち・完了を区別する。再試行は調査全体で数え、担当の切り替えで上限をリセットしない。動作を追いにくい自動継続や多重の制御を増やさず、状態と証拠から次の担当・作業が分かる形を保つ。

## 一度の再現から原因を追えるようにする

- 入力、起動条件、実行したビルド、端末・描画環境を記録し、再実行できるようにする。時間や乱数が重要な場合は固定するか記録する。
- 画像と内部状態を、同じ実行・フレーム・対象に結び付ける。問題に必要な操作列や状態遷移も残す。
- 取得失敗、タイムアウト、未対応、データ欠落を、正常値や「問題なし」と区別する。

報告では要点と証拠への参照を示し、保存された生データから必要な範囲を追加取得できるようにする。一時的な証拠の保存先はリポジトリの規約に従う。継続利用する再現入力や判定基準は、テスト等の保守対象へ移す。

## 必要な情報だけを取り出せるようにする

AIと人間が同じ証拠を使えるよう、構造化した状態に単位や対象識別子を付け、人間向けの要約や可視化をそこから作る。全ログの常時出力を前提にせず、カテゴリ・対象・期間で絞れるようにする。

高頻度の事象には集計や必要区間の記録を使う。要約や間引きによって異常が隠れる場合に備え、その区間の詳細を取得できるようにする。計測が実行時間や同期を変えて症状に影響しうる場合は、計測の有無を比較する。

## 自動操作と利用者の操作をつなぐ

操作APIは、UIと共通の処理を通して準備・実行・観測を省力化する。操作の受理と処理の完了を区別し、完了・失敗・待機状態を取得できるようにする。固定時間の待機だけに成功判定を依存させない。

APIで省略した操作は明示し、入力経路を検査する場面では実際の操作を使う。人間の操作が必要な場合は、AIで準備と証拠回収を済ませ、依頼を必要な操作や判断に絞る。

## CPU・GPU境界を観測する

CPU側の値から転送内容、GPUでの処理、最終画像まで、問題のある段階を区別できるようにする。

- 意味・単位・座標系と、バイト配置・要素数・有効範囲を区別して検証する。CPU側の型だけで境界全体を保証したとは扱わない。
- 対象のバッファや中間画像など、原因候補を判別するために必要なものを選んで取得する。
- 読み戻した値と最終画像が、どのフレーム・入力・描画条件に対応するかを記録する。

シェーダー、フレームキャプチャ、GPU計測、環境間の差に専用のskillが用意されている場合は、対象実装に対応するものだけを使う。
